# Retro – Multi-Perspektiven-Analyse + OpenRouter/Nemotron-Integration (22.07.2026)

Rückblick auf einen zweiteiligen Loop: (1) fünf parallele Agenten-Analysen (Architektur, Produkt/UX, Security, KI-Strategie, Performance/Ops) auf `docs/WEITERENTWICKLUNGSPOTENZIAL_2026-07-22.md`, (2) direkt im Anschluss Umsetzung eines Teils der Befunde plus Anbindung von Nemotron über OpenRouter als drittem KI-Provider.

## Was gut funktioniert hat

- **Fünf unabhängige Agenten mit klar getrennten Linsen statt eines generischen Reviews.** Jeder Agent bekam einen konkreten Fokus (Architektur, Produkt, Security, KI, Performance) plus bereits bekannten Kontext aus `HANDOFF_2026-07-21.md`, mit expliziter Anweisung "geh tiefer als die bekannten Punkte". Zwei Agenten (Architektur, Performance) kamen unabhängig zum selben Sync-Engine-Fund (Voll-Pull + N+1) - dieses Cross-Validierungssignal wäre bei einem einzelnen Review-Durchgang nicht sichtbar geworden.
- **Vor der Implementierung den Bestandscode wirklich gelesen statt vom Analyse-Bericht ausgegangen.** Das Nachschauen in `runtime.js`, `app.js`, den Migrationen und `services/settings.ts` deckte einen eigenständigen, vom Analyse-Bericht nicht erfassten Bug auf: `ai_provider` war im Frontend-Code referenziert, existierte aber nie als DB-Spalte - Speichern der Provider-Wahl schlug für echte Nutzer seit jeher fehl. Ohne diesen Zwischenschritt wäre die Nemotron-Integration auf einer kaputten Grundlage aufgesetzt worden.
- **Sicherheitsanforderung aus der Analyse direkt mit der neuen Provider-Integration verknüpft**, statt getrennt zu behandeln: Da ein dritter kostenpflichtiger Provider dazukam, wurde das Fehlen von Auth/Rate-Limiting auf `/api/ai/*` (Security-Fund #1) im selben Zug behoben - beides zusammen zu machen war günstiger als zwei getrennte Loops.
- **CI-Implikationen einer Middleware-Änderung vorab durchdacht statt hinterher entdeckt.** Vor dem Schreiben der Auth-Middleware wurde geprüft, wie `server/.env` in CI befüllt wird (`ci-deploy.yml`) und wie `dotenv.config()` in `app.js` tatsächlich den Pfad auflöst (cwd-abhängig, bricht unter `vitest run` vs. `npm run server`). Beides wurde korrigiert (CI-Workflow ergänzt, `dotenv.config({path pfad relativ zum Modul})`), bevor der Auth-Check scharf geschaltet wurde - dadurch brach kein bestehender Test.
- **Reale Lücke lokal verifiziert statt angenommen**: Server tatsächlich gestartet und `/api/ai/search` ohne Token angefragt, um das erwartete Fail-Closed-Verhalten zu bestätigen, statt nur auf Codelesen zu vertrauen.

## Was nicht gut funktioniert hat

- **`npm install` war in dieser Sandbox nötig, aber nicht vorab eingeplant.** `node_modules` existierte zu Beginn nicht (weder root noch `server/`), was `typecheck` zunächst mit einer irreführenden Fehlermeldung (`Cannot find type definition file for 'node'`) scheitern ließ, die aussah wie ein echtes Typproblem statt eines fehlenden Installs. Lektion: bei einer frischen Sandbox-Session zuerst `ls node_modules` prüfen, bevor Testergebnisse inhaltlich interpretiert werden.
- **Scope-Entscheidung ("was wird jetzt umgesetzt, was nicht") wurde implizit getroffen statt mit dem Nutzer kurz abgestimmt.** "Implementiere" plus der Nemotron-Wunsch wurden als "Quick-Wins + Nemotron, große Architektur-Punkte später" interpretiert, ohne das explizit zu bestätigen. Ist in diesem Fall vermutlich im Sinne des Nutzers, aber bei einem so großen Analyse-Dokument (drei Aufwandsstufen) wäre eine kurze Nachfrage zur gewünschten Stufe risikoärmer gewesen als eine stillschweigende Annahme.
- **Playwright/E2E-Pfad wurde nur per Code-Grep auf Betroffenheit geprüft, nicht tatsächlich lokal ausgeführt** (kein Docker/Supabase in dieser Sandbox verfügbar, bereits aus früherem Loop bekannt). Die Auth-Gate-Änderung an `/api/ai/*` sollte sich laut Grep nicht mit `tests/ui/*` überschneiden, das bleibt aber bis zum ersten echten CI-Lauf eine Annahme statt ein Beweis.
- **OpenRouter-Modell-Slugs (Nemotron-Varianten) wurden nicht gegen die Live-API verifiziert** (kein Netzwerkzugriff auf OpenRouter in dieser Sandbox) - die gewählten Modell-IDs basieren auf Trainingswissen und sollten vor dem ersten Produktiveinsatz gegen `https://openrouter.ai/api/v1/models` abgeglichen werden.

## Nachtrag: Pivot auf "nur OpenRouter" + erster echter CI-Lauf

Direkt im Anschluss kam die Anweisung, ausnahmslos alle KI-Anbindungen über OpenRouter zu führen statt Gemini/OpenAI weiter direkt per SDK anzusprechen. Das war ein guter Zeitpunkt dafür, weil der Nemotron-Umbau bereits das Muster (OpenAI-kompatibler Client, `:online`-Plugin, Fallback-Ketten) etabliert hatte - die Konsolidierung auf drei "Modell-Familien" statt drei getrennte Provider-Module war dadurch eine Vereinfachung, keine Erweiterung der Komplexität. Nebeneffekt: alle drei Familien bekommen jetzt einheitlich echtes Web-Grounding, nicht nur der OpenAI-Pfad wie vorher.

- **Der erste echte CI-Lauf nach dem vorherigen Push fand tatsächlich einen Fehler, den lokales Testen nicht hätte finden können**: Die pgTAP-RLS-Suite legte eine Fixture-Zeile in `public.ai_cache` an und prüfte fünf Assertions dagegen - genau die Tabelle, die in derselben Änderung als "toter Code" gedroppt wurde. Lokal lief `npm run test:unit` grün, weil pgTAP nur in CI (mit echtem Postgres) läuft, nicht unter Vitest. Bestätigt Punkt 17 oben: Annahmen über CI-Auswirkungen ohne echten CI-Lauf bleiben Annahmen, unabhängig davon wie sorgfältig der Code vorher gelesen wurde.
- **Lektion für nächste Migrations-/Test-Änderungen**: Wenn eine Migration eine Tabelle droppt oder umbenennt, IMMER zuerst `grep -rn <tabellenname> supabase/` (inkl. `supabase/tests/`, `supabase/seed.sql`) prüfen, nicht nur den Anwendungscode (`server/`, `services/`) - pgTAP-Fixtures sind leicht zu übersehen, weil sie in einem separaten Testbaum liegen, der nur in CI ausgeführt wird.
